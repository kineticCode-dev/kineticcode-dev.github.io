# The four Qt::ConnectionType values: what really happens when you write connect()

In the previous three modules you wrote dozens of `connect()` calls between objects living on different threads, and every time you let Qt decide on its own how to deliver that call. It always worked, and rightly so — that's the default behavior, designed precisely so you don't have to think about it most of the time. But behind that quiet default there's a precise mechanism, with four explicit modes, and today we take it apart completely: not to complicate your life, but because the day something behaves in a way you don't expect — a value that arrives late, an application that freezes for no apparent reason — the first question to ask yourself will be exactly "what kind of connection was this, really?".

Every time you call `connect()`, the last parameter — almost always omitted — is a value from the `Qt::ConnectionType` enumeration. Omitting it gets you `Qt::AutoConnection`, the default. But hiding behind that default are three other explicit behaviors, and understanding all four is the only way to really know what happens when you write `emit`.

## DirectConnection: a function call, nothing more

`Qt::DirectConnection` is the conceptually simplest case, even though it's the one where most mistakes happen when it's chosen carelessly. With this mode, `emit signal(...)` translates, literally, into a synchronous call of the slot — as if you had written `object->slot(...)` by hand. There's no queue, no event, no event loop involved anywhere: the thread executing `emit` is the same thread that executes the body of the slot, from start to finish, before `emit` even returns.

![The four Qt::ConnectionType modes compared](modulo-04/17-connection-types-qt.png)

When sender and receiver live on the **same** thread — the most common case for `DirectConnection`, and exactly what `AutoConnection` would choose in that situation — this behavior is not only safe but also the most efficient possible: no marshalling cost, no event allocation, no trip through a queue. The problem arises when you force `DirectConnection` **across different threads**: at that point the slot really executes on the *sender's* thread, not on the one the receiver "belongs" to — and if that slot touches member variables of the receiver without its own internal protection (a `QMutex`, for instance), you have recreated from scratch exactly the data race that Module 0 taught you to recognize. A `DirectConnection` forced across threads is safe only when the slot's code is genuinely *reentrant-safe* — it doesn't touch any unprotected shared state, or protects it itself with its own tools — and that's a situation rare enough to be treated as an exception, never as a habit.

## QueuedConnection: the default across threads, and why it's safe by construction

`Qt::QueuedConnection` is the behavior you've already been relying on, without ever specifying it explicitly, since Module 1: `emit` does **not** call the slot on the spot. It packages the call — which slot, with which arguments, copied rather than passed by reference — into an event object, and deposits it into the event queue of the thread the receiver belongs to. The sending thread, right after the `emit`, carries on with its own business: it doesn't wait for the slot to execute, it doesn't even know exactly when that will happen. The receiving thread, when it reaches its own turn in the cycle of its event loop — the same mechanism behind `exec()` you saw in Module 1 — pulls the event out of the queue and only then does it actually execute the slot, with its arguments, on its own thread.

This is precisely the reason a queued connection is thread-safe by construction, without needing any mutex from you. There is never a moment when two threads simultaneously execute code touching the same object through that connection — emission and execution are separated in time, and that separation is guaranteed by the queue. The price you pay is that the signal's arguments must be **copyable** (Qt copies them into the event) and that custom types passed as arguments must be registered with `qRegisterMetaType<T>()` if they aren't already known to Qt's meta-type system — a detail you rarely notice with `int`, `QString`, or `long long`, but one that becomes relevant the day you want a custom struct of yours to travel through a cross-thread signal.

## BlockingQueuedConnection: like Queued, but the sender waits

`Qt::BlockingQueuedConnection` takes exactly the mechanism of `QueuedConnection` — the event is still posted to the receiver's queue — and adds a constraint: the sending thread blocks after the `emit`, and doesn't resume until the slot has finished executing on the receiving thread. It's a kind of completion acknowledgment that unblocks whoever emitted.

What's it for, if `QueuedConnection` is already safe and doesn't block anyone? It's for all the cases where the sender genuinely needs to **know that the slot has been executed** before proceeding — not just that it's been queued. The most direct case is when you want to read a return value from the slot (we'll come back to this in the next article, about `QMetaObject::invokeMethod`): with an ordinary `QueuedConnection` you'd have no way to wait for the result, because `emit` returns immediately, well before the slot has even started. Another legitimate case is when the relative ordering between two cross-thread operations really matters and you can't afford the temporal uncertainty of an asynchronous queue.

The price, however, is high: **if sender and receiver are the same thread, `BlockingQueuedConnection` produces a guaranteed deadlock**. The sender blocks waiting for the event to be processed by the receiver's event loop — but if receiver and sender are the same thread, that event loop is exactly the thread that just blocked waiting. It will never go back to spinning to process the event it itself posted, because it's stopped waiting for someone to process it. It's a circular wait with a single participant, conceptually identical to the two-thread deadlock seen in Module 2, just compressed into a single actor. Qt, in debug builds, often detects this situation and prints an explicit warning at runtime — but don't count on it: it's a diagnostic safety net, not a structural protection. The practical rule has no exceptions: **never use `BlockingQueuedConnection` unless you're certain, by construction of your program, that sender and receiver live on different threads**.

## AutoConnection: the decision made at emission time, not at connect() time

We arrive at the default behavior, the one you've always used implicitly, and its most important subtlety. `Qt::AutoConnection` isn't a fifth mode in its own right: it's a *deferred* choice, which Qt resolves into `DirectConnection` or `QueuedConnection` by looking at the thread affinity of sender and receiver — but looked at **when**? The answer is: at the moment the signal is actually emitted, not at the instant you wrote the `connect()` line.

Why does this distinction matter so much? Because the thread affinity of a `QObject` is **not immutable**: you can change it at any moment with `moveToThread()`, as you've done in every guided project of this course. Imagine a `connect()` written when sender and receiver live on the same thread — at that instant, if the signal were emitted, the connection would resolve to `DirectConnection`. But if, before the next emission, you move the receiver to another thread with `moveToThread()`, the **very same connection**, without you touching it again, will resolve that time to `QueuedConnection` — because Qt rechecks the two thread affinities every single time the signal is emitted, not just once when you wrote `connect()`. It's a detail that rarely changes your program's behavior in practice (usually you move an object to a thread once, at the start, and never touch it again), but understanding it saves you an entire class of phantom bugs: if you observe that the same connection behaves differently at different points in execution, the first question to ask is whether the thread affinity of one of the two objects changed in the meantime — not whether `connect()` is "behaving inconsistently", which it never does.

In the producer-consumer example of Module 2 you already saw a concrete case of this behavior, even though it wasn't pointed out explicitly at the time: the shared buffer object retained thread affinity on the GUI thread, but its occupancy signal was emitted from inside the production/consumption methods, called directly by the Producer's or Consumer's thread — so the emission happened on a thread different from the one the *sender itself* formally belonged to. What matters, in that case, for deciding `AutoConnection`? Always the thread affinity of the **objects** involved in `connect()`, compared against the thread that **is executing the emit at that moment** for the sender, and against that of the receiver — not "where the sender object lives" on paper, but which thread the `emit` call is actually being made from. The question Qt asks itself is always "is the CURRENT thread, right now, the same as the receiver's?" — not "where was the object that owns the signal created?".

With these four behaviors finally told apart, you're ready for the next step: a way to call methods across threads without even going through a signal-slot pair declared in advance, and a pattern for stopping a worker without ever shutting it down by force.
