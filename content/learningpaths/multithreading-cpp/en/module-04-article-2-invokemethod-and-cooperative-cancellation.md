# QMetaObject::invokeMethod and cooperative cancellation: calling and stopping a thread without risk

In the previous article you took apart the four `Qt::ConnectionType` values. Everything you've done so far to communicate across threads, though, went through a signal-slot pair declared in advance: you define a signal in the sending class, a slot in the receiving one, connect them with `connect()`, and from that moment on every `emit` marshals the call according to those rules. It works beautifully for **recurring** communication — a worker that repeatedly emits progress, a window that sends commands every time the user clicks a button. But what do you do when you need **a single occasional call**, maybe with different arguments each time, to a method you don't want to promote to a dedicated signal/slot pair just for that one use?

## QMetaObject::invokeMethod: calling a method without a dedicated connect()

`QMetaObject::invokeMethod()` solves exactly this case. It's a static function that takes a pointer to a `QObject`, the name of a method (as a string, or — in the more modern Qt 6 overloads — a function pointer or a lambda), an explicit `Qt::ConnectionType`, and the arguments to pass, packaged with the `Q_ARG(Type, value)` macro. The delivery mechanism is **identical** to that of an ordinary queued connection — the call gets marshalled through the receiving thread's event queue — but without you having to declare a signal in advance and connect it with `connect()`. The only requirement on the target method is that it be marked `Q_INVOKABLE` (if it's an ordinary public method) or that it already be an existing slot: in either case, Qt's meta-object system knows how to find it and invoke it by name at runtime.

![QMetaObject::invokeMethod delivering a call safely without a dedicated connect()](modulo-04/18-invokemethod-safe-call.png)

As with an ordinary `connect()`, you can choose the connection type: `Qt::QueuedConnection` for a *fire-and-forget* command, where the caller doesn't wait for anything and moves on right away, or `Qt::BlockingQueuedConnection` when you need **the return value** of the invoked method. With the latter, you additionally use the `Q_RETURN_ARG(Type, destinationVariable)` macro: the calling thread blocks until the method has really executed on the receiving thread and has written its return value into the variable you passed it. It's the one clean way to synchronously read a value computed on another thread without having to invent your own waiting mechanism with a mutex and a wait condition just for that single purpose.

It's worth noting something you may not have connected yet: you've already *used* `QMetaObject::invokeMethod` indirectly, even if you never wrote it by hand. It's precisely the mechanism Qt uses internally when you call `deleteLater()` from another thread (Module 1), and it's conceptually related to how `QTimer::singleShot` with a receiver on another thread marshals its own call. It's not some exotic function on the fringes of Qt: it's a fundamental building block that usually stays hidden behind more convenient APIs, and today you learn to use it directly.

One clarification that will save you an afternoon of debugging: the deadlock rule for `BlockingQueuedConnection` seen in the previous article applies here identically. If you call `QMetaObject::invokeMethod(object, "method", Qt::BlockingQueuedConnection, ...)` and `object` lives on exactly the thread you're calling from, you block forever, for the very same reason.

## Cooperative cancellation: stopping a worker without shutting it down by force

In Modules 1 and 2, your worker had a simple life cycle: it started, did its work through to the end, and the window waited with `quit()` + `wait()`. You never really had to face the problem of **interrupting** a job midway, on the user's explicit request, while it's still in progress. The standard solution has a name: **cooperative cancellation**.

The underlying idea is simple: the worker, within its own loop, periodically checks a shared boolean flag — "should I stop?" — and when it finds it `true`, it exits the loop on its own, at a point it chose itself, where it knows it's not leaving anything half-done. Nobody "shuts down" the worker from the outside: it's the worker itself, cooperating, that decides when it's safe to stop. Hence the name.

### Why std::atomic<bool>, not just bool

The flag we'll use is a `std::atomic<bool>`, not a plain `bool`. What would change with an ordinary `bool`? It's not about data corruption as such — a `bool` is so small that almost no real architecture produces a "half" write to it. The real problem is subtler, and it's exactly what Module 5 covers in full depth when it reaches the C++ memory model: **cross-core visibility**. Modern CPUs don't write a value directly to RAM every time and don't reread it from there every time: each core has its own caches, and without an explicit synchronization mechanism, a thread running on one core can go on seeing, for an indefinite time, the old value of a variable that another thread, on another core, has already modified — not because the data is corrupted, but because that write hasn't "arrived" at the first core's cache yet. The compiler itself, absent different guarantees, is free to optimize away the very act of repeatedly rechecking the flag inside the loop, keeping it in a register instead of rereading it from memory every iteration.

`std::atomic<bool>` solves both problems with a single guarantee from the language: every `load()` and every `store()` on an atomic variable has a well-defined synchronization relationship with the other atomic operations on that same variable, the compiler cannot optimize away the rereads, and — with the default ordering (*sequentially consistent*, what you get without specifying anything else) — a write made by one thread is guaranteed to be visible to another thread that performs a subsequent read on the same atomic variable. You don't need to understand the full taxonomy of the memory model today (relaxed, acquire/release, sequentially consistent: it comes with all the rigor it deserves in Module 5) — for now, the practical principle is enough: **a cancellation flag shared between threads must be atomic, not simply boolean**, because the guarantee you need isn't "no corrupted bits", it's "the other thread will really see the new value within a reasonable time, not a value frozen in cache".

The complete pattern is a `while (!m_stop.load())` wrapping a single step of work, with the flag being written (`m_stop.store(true)`) by the GUI thread in response to a click. Every iteration of the loop is a natural checkpoint: if the flag is true, the worker exits, and no resource is left half-done — the mutexes acquired within that step have already been released before the next check, the C++ destructors of objects local to that step have already run, the shared state is in a coherent state.

## QThread::terminate(): why it exists, and why it should (almost) always be avoided

If cooperative cancellation feels like a long detour for a problem that would seemingly be solved with a single call, you're right to ask yourself: why not just use `thread->terminate()`? The method really does exist in `QThread`'s API, and it does exactly what the name promises — it **terminates the operating-system thread immediately**, at the exact point its execution happens to be, without warning it, without giving it any chance to react.

The problem is precisely in that brutality. The worker gets interrupted at an arbitrary point — potentially **inside** a critical section protected by a mutex it had just acquired and not yet released. The operating system does nothing to unlock it: that mutex stays locked forever, and every other thread that in the future tries to acquire it will wait indefinitely — a deadlock nobody "programmed" but that the forced shutdown created as a side effect. Worse still: `terminate()` runs **no C++ destructor at all** for objects that lived on that thread's stack at the moment of interruption — no `QMutexLocker` unlocks automatically via RAII (the RAII mechanism itself presupposes that control flow passes through the destructor, something an operating-system-level shutdown bypasses entirely), no file gets closed cleanly, no allocated resource gets released. The result is a program state that's potentially **inconsistent midway through**: a data structure that was about to be updated in two steps and only received one, a buffer with an advanced index but its content not yet written.

![Cooperative cancellation compared with QThread::terminate()](modulo-04/19-cooperative-cancellation-vs-terminate.png)

To be fully honest: `terminate()` is *never* completely forbidden by Qt's official documentation, and in extreme cases — a third-party thread that you know for certain never touches shared state, that you must stop at any cost because it's entered an unrecoverable infinite loop, in a context where losing that process messily is acceptable — it can be the last resort available. But in 99% of the cases you'll run into writing application-level Qt code, "the thread stopped responding and I want to kill it" is the symptom of a design problem in the worker (a loop that never checks any flag, a wait that nobody ever wakes), not a justification for `terminate()` — the correct cure is almost always to make that worker cooperatively cancellable with the pattern just shown, not to force its death from the outside.

With `invokeMethod` and cooperative cancellation in your toolkit, you're ready for this module's guided project: a worker with a complete life cycle — start, pause, resume, stop — that puts exactly these ideas into practice, including a real deadlock that was made, and then fixed, while preparing this very course.
